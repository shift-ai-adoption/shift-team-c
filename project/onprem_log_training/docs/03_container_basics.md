# コンテナの説明と仮想マシンとの違い

## この資料の目的

この環境では `server`(機能サーバ役)をDockerコンテナとして動かしています。
ここでは、コンテナとは何か、従来の仮想マシン(VM)とどう違うのかを整理します。

## コンテナとは

コンテナは、「アプリケーションを、それが動くために必要なファイル・設定・依存関係ごと
1つにパッケージ化し、他の環境から隔離された状態で実行する」技術です。

この環境の `server` を例にすると、コンテナの中には次のものが含まれています。

- Node.jsの実行環境
- `server/` 配下のアプリケーションコード(`server.js` など)
- 必要なライブラリ(`npm install` した内容)
- SSHサーバー(学習者のAIエージェントが接続するため)

これらが1つの「イメージ」としてまとめられ、`docker run` (または `docker compose up`)を
実行すると、その内容がそのまま「コンテナ」として起動します。

## 仮想マシン(VM)とコンテナの違い

もっとも大きな違いは、**OS(オペレーティングシステム)をどこまで独立させるか**です。

```
[仮想マシン(VM)の構成]              [コンテナの構成]

┌─────────────┬─────────────┐      ┌─────────────┬─────────────┐
│   アプリA    │   アプリB    │      │   アプリA    │   アプリB    │
├─────────────┼─────────────┤      ├─────────────┼─────────────┤
│  ゲストOS    │  ゲストOS    │      │  (OSは共有)  │  (OSは共有)  │
├─────────────┴─────────────┤      ├─────────────┴─────────────┤
│      ハイパーバイザー        │      │      コンテナエンジン        │
├───────────────────────────┤      │        (Docker等)         │
│        ホストOS            │      ├───────────────────────────┤
├───────────────────────────┤      │        ホストOS            │
│          物理マシン          │      ├───────────────────────────┤
└───────────────────────────┘      │          物理マシン          │
                                    └───────────────────────────┘
```

| 観点 | 仮想マシン(VM) | コンテナ |
|---|---|---|
| OS | アプリごとに独立した「ゲストOS」をまるごと起動する | ホストOSのカーネルを共有し、アプリ実行環境だけを分離する |
| 起動時間 | OS起動を含むため数十秒〜数分 | OS起動が不要なため数秒以内 |
| サイズ | ゲストOS一式を含むため数GB単位になりやすい | 必要なファイルだけなので数十MB〜数百MB程度 |
| 隔離の強さ | OSレベルで完全に分離される(強い) | プロセスレベルの分離(VMより弱いが実用上十分) |
| 主な用途 | 異なるOS自体を動かしたい場合、強い隔離が必要な場合 | 同じOS系列で、アプリ単位を素早く量産・配布したい場合 |

簡単に言うと、VMは「コンピュータそのものを複数台分、仮想的に用意する」方式で、
コンテナは「1台のコンピュータの中で、アプリの実行環境だけを部屋分けする」方式です。

## この環境でコンテナを使っている理由

`server` をコンテナ化しているのは、次の理由からです。

1. **同じ環境を誰でも再現できる**: `docker compose up` だけで、OSやNode.jsのバージョンの
   違いに悩まされずに同じ`server`環境を起動できます。
2. **実際のオンプレ運用に近い形を体験できる**: 実務では、ログを出しているサーバーに
   直接ログインするのではなく、コンテナ化されたサービスに対してSSHなどでアクセスして
   調査する場面が多くあります。この環境はその状況を模しています。
3. **後片付けが簡単**: `docker compose down` でコンテナを丸ごと削除すれば、ホスト側の
   環境を汚さずに元の状態に戻せます。

## コンテナ利用の基本的な流れ(この環境での例)

```
[Dockerfile]                [イメージ]                [コンテナ]
何を含めるかの                docker build             docker run で
「設計図」                 ──────────────▶  で作った   ──────────────▶  実際に動いている
                            「完成品」の雛形              実行中のプロセス
```

1. **Dockerfile** — どのOS・ライブラリ・アプリコードを含めるかを記述した設計図
   (この環境では `docker/Dockerfile`)
2. **イメージ(image)** — Dockerfileをもとに実際にビルドされた、実行可能な完成品
3. **コンテナ(container)** — イメージを実際に起動した、動作中のインスタンス

同じイメージから何度でも同じ内容のコンテナを起動できるため、「毎回まったく同じ状態から
やり直せる」という再現性の高さが、この環境の学習体験にも活かされています。

## 補足: この環境における注意点

学習用途のため、通常の本番運用では避けるべき簡略化を行っています(セキュリティを
意図的に考慮していません)。

- SSHの秘密鍵をリポジトリに平文で同梱している
- コンテナ内でSSHサーバーを常時起動状態にしている

実際の業務でコンテナを扱う際は、これらは避け、鍵の管理やアクセス制御を別途検討する
必要があります。
