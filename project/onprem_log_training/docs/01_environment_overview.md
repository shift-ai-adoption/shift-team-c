# この研修環境の説明

## この環境は何のためにあるか

この環境(`onprem_log_training`)は、学習者がAIエージェント(Claude Codeなど)を使いながら、
「ログに関連するツールやアプリ」を自分の手で作ってみるための練習環境です。

実際の業務システムでは、複数のサーバー(アプリケーションサーバー、業務ロジックを担う機能サーバーなど)
がそれぞれ独立にログを出力しており、障害が起きたときは「どのサーバーの、どの時刻の、どのログが
同じ処理に関するものか」を人手またはツールで突き合わせる必要があります。この環境では、その状況を
小規模かつ安全に再現しています。

## 全体構成

環境は次の2つのサーバー役で構成されています。

| 役割 | 何をするか | 動き方 |
|---|---|---|
| **client**(アプリケーションサーバ役) | ブラウザからのアクセスを受け付け、画面やAPIを提供する | Dockerコンテナとして動作(SSHは搭載せず、ログはホストへ直接マウント) |
| **server**(機能サーバ役) | 在庫確認や注文金額の計算など、実際の業務ロジックを処理する | Dockerコンテナとして動作し、SSHでログにアクセスできる |

`client` が受け付けたリクエストは、内部で `server` へHTTP経由で問い合わせを行います。
つまり、ブラウザ操作 → `client` → (ネットワーク越しに) `server` → 結果を`client`へ返す、
という2段階の処理になっており、実際の複数サーバー構成を模しています。

## TrackIDという考え方

1つのユーザー操作(例:商品詳細ページを開く)が発生すると、`client` はその操作に対して
7文字のランダムな識別子(**TrackID**)を1つ発行します。この TrackID は `client` から `server` への
問い合わせにもHTTPヘッダとして渡され、`server` 側のログにも同じ TrackID が記録されます。

```
ブラウザ操作
   │
   ▼
client (TrackID: ABC1234 を発行)
   │  HTTPヘッダ X-Track-Id: ABC1234 を付けて問い合わせ
   ▼
server (受け取った ABC1234 を自分のログにも記録)
```

結果として、次の2つのログファイルに **同じ TrackID** が残ります。

- `client/logs/app.log` ― ホストのローカルファイル(コンテナの `/app/logs` をbind mountしているため、
  SSH不要でホストから直接読めます)。ブラウザから見えるリクエストの記録。
- `server/logs/service.log` ― コンテナ内のファイル。業務ロジック側の処理記録。

**この「同じ TrackID が複数のログに分散して残る」という状態が、この研修環境の核心です。**
学習者はこれを手がかりに、複数サーバーのログを1つのインシデントとして紐づける方法を
自分で(あるいはAIエージェントに指示して)組み立てていきます。

## わざと仕込まれた不具合

体験しやすくするため、`server` 側の業務ロジックには2つの不具合があらかじめ仕込まれています
(`server/bug-config.json` で有効/無効を切り替え可能)。

1. 在庫切れ商品の詳細ページを開くとエラーになる不具合
2. 「請求書払い」で注文確定するとエラーになる不具合

どちらもブラウザ操作から実際にエラーを発生させ、その際に払い出される TrackID を
2つのログファイルから探し出す、という一連の流れを体験できます。

## AIエージェントとの関わり方

この環境自体は「ログを出す側」の土台を用意するだけで、**ログを収集・分析するツールは
用意していません**。学習者は、AIエージェントに指示を出しながら、

- `client` のログを監視してエラーを検知する
- そこからTrackIDを取り出す
- `server` 側のログをSSH経由で検索し、同じTrackIDの記録を探す
- 2つのログを1つのインシデントとしてまとめる

という一連のツール(いわゆる「ログコレクター」)を自分で作っていきます。
SSH接続に必要な情報(接続先ホスト・ポート・鍵・ログの場所など)は `AGENT_SSH_GUIDE.md` に
まとめてあり、これをAIエージェントに読み込ませることで、学習者自身がSSHの詳細を覚える必要は
ありません。
